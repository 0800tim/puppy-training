Commits reviewed: `5756c8c` (socialisation checklist, timeline, breed notes), `e92ab39` (design pass: icon sprite, hero, no emoji tiles) and `800c1d2` (design pass two: surface hierarchy, floating tab bar, edge-cache fix). Reviewed on 17 October against the questions on the burn board.

## Version stamps stay in step

`public/sw.js` has `VERSION = "pt-v11"` and every app file in `public/index.html` is referenced with `?v=11`. `scripts/bump.mjs` (added in `800c1d2`) is the only way either should change: it reads the current number from `sw.js`, writes the next one to both files, and prints the change. The service worker builds its shell list from the same number, so the cached URLs match what the page loads. Verified: one number, two files, one script. **Pass.**

Risk noted: two branches open today (`burn/security-review`, `burn/accessibility`) each ran the bump independently and both landed on `pt-v12`. Whoever merges runs `node scripts/bump.mjs` once more afterwards; the clash is a one-line merge conflict, not a logic problem.

## Dark-mode tokens used consistently

Every colour in `styles.css` after the two `:root` blocks is either a token or one of: `#fff`/`#000` on surfaces that are the same in both themes (icon discs, the video backdrop), `#cfc8ff`/`#ffb38a` inside the always-dark video overlay, and three literals that should have been tokens: the hero gradient (`#5b4bf0`, `#8257ff`) and the level badge's ink (`#1c1a33`). The hero was hard-coded so it stays violet in dark mode, which is right, but it belongs in the token blocks so a theme can tune it. **Fixed in this branch**: `--hero-a`, `--hero-b`, `--hero-ink` in both blocks, slightly deeper in dark mode. The level badge ink stays literal because it sits on the fixed yellow `--sun`.

Dead tokens: `--hdr`, `--hdr2`, `--hdr-soft` and `--on-hdr` are no longer read now that the header is a plain surface (`800c1d2`). Harmless; remove in the next stylesheet tidy.

## Socialisation data matches the server's validation

`content.js` holds 7 groups and 60 items. The server does not keep its own list: `SOCIAL_ITEMS` is built at start from `CONTENT.socialGroups` as `<group id>:<index>`, and `PUT /api/social/:item` matches `^[a-z]+:\d+$` then checks the set. Group ids are lowercase letters only, so the route pattern accepts every real key and nothing else. Adding or reordering an item in `content.js` changes the keys, which would orphan logged entries. **Pass**, with one note: keys are positional, so the next content edit that inserts an item mid-list should append instead. Documented in `docs/ARCHITECTURE.md`.
